# 交付说明：UDP 双端口出口运维演练

## 做成了什么

**拓扑（`docker compose up --build` 起三个容器）**

| 容器 | 作用 | 端口 |
| --- | --- | --- |
| `gateway` | FastAPI 演练页 + UDP 网关 + 三个本地客户端 | 网页 `127.0.0.1:8000`（仅此端口发布到宿主机） |
| `echo-a` | 回显服务 A，回包延迟 0–2 s | compose 网络内 `udp/16001` |
| `echo-b` | 回显服务 B，回包延迟 0–2 s | compose 网络内 `udp/16002` |

网关为每个上游各开一个 UDP 入口（`udp/15001` → A，`udp/15002` → B），出口只有两个端口
（`udp/17000`、`udp/17001`）。三个客户端是网关进程内三个独立绑定的 UDP 套接字
（`127.0.0.11/12/13:随机端口`），发包是真 UDP，走真实的内核套接字和容器网络，
不是页面里模拟的。端口号可用环境变量调整（`EGRESS_PORTS`、`ECHO_A_HOST` 等，见 `compose.yaml`）。

**会话规则（`app/gateway_core.py`）**

- 会话键 =（客户端 IP、客户端端口、上游）。
- 同一会话后续的包沿用原出口端口，并刷新「最后向上游转发」时间。
- 同一上游同一时刻一个出口端口只能承载一个会话；**不同上游可以共用同一个出口端口**。
- 会话在最后一次向上游转发后满 1 秒失效。
- 失效后 `(原出口端口, 该上游)` 组合再保留 2 秒：该组合的回包一律丢弃；端口本身立刻可以
  分配给**其他上游**（同一上游要等保留期结束）。
- 有可用端口就转发；没有则**不向上游发包**，网关回一条 `gateway_error`，网页在对应客户端
  卡片和事件日志里写明是哪个端口、被「同一上游的活动会话」还是「迟到回包保留期」占着、
  还剩多少秒。
- 回包按「到达的出口端口 + 来源上游」查活动会话，只送给该会话对应的客户端；命中保留期记
  `drop_late`，查不到会话记 `drop_unknown`。

**网页（`app/static/index.html`，2 Hz 轮询 `/api/state`）**

- 0–2000 ms 回包延迟滑块（≥1000 ms 时高亮提示会触发迟到丢弃），可填消息内容。
- 三个客户端卡片：各自本地地址、发往哪个上游、实时收件箱（显示回显服务名、**网关出口端口**、
  实际延迟、RTT、字节数、上游响应地址，或网关给出的未转发原因）。
- 出口端口面板：每个端口上的活动会话（寿命进度条）与保留期组合（剩余时间），空闲态。
- 会话表、计数器、事件日志（forward / deliver / reject / drop_late / drop_unknown /
  session_expired / quarantine_ended / reset）。
- 快捷按钮：全部发送（1→A、2→B、3→A）、2 并发到 A、3 并发到 A（演示无可用端口）、重置。

**其它文件**：`Dockerfile`、`Dockerfile.echo`、`compose.yaml`、`requirements*.txt`、`pytest.ini`、
`tests/`、`scripts/verify_api.py`、`scripts/check_compose.py`、`README.md`。

## 测到了什么

**单元测试（假时钟，`tests/test_gateway_core.py`，14 个）**：端口分配与复用、同上游会话独占端口、
会话复用与续期、1 s 失效、2 s 组合保留、保留期内端口可给另一上游、保留期阻塞同上游、迟到回包丢弃、
回包只投递给会话所属客户端、无端口原因文本、单端口配置、重置清空、非法配置拒绝。

**集成测试（真实 UDP 套接字 + 真实回显，`tests/test_integration.py`，5 个）**：三客户端双上游往返、
无可用端口时客户端收到拒绝、1500 ms 迟到回包被丢弃且端口复用后不串包、1 s 内续期、未知来源回包丢弃。
`python3 -m pytest -q` → **19 passed**，`ruff check` 无告警。

**对运行中的服务实发（`python3 -I scripts/verify_api.py`，连续 3 轮均 exit 0，19/19 项 PASS）**：

| 场景 | 实测结果 |
| --- | --- |
| 1→A / 2→B / 3→A，0 ms | 三客户端都收到真实回包；1 和 2 共用出口 **17000**；3 到 A 用 **17001**；上游看到的源地址就是网关出口端口 |
| 1→A、2→A、3→A | 前两个占满 17000/17001；第三个 **未上游转发**，客户端收到「无可用出口端口…17000/17001 被同一上游的会话占用（会话剩余 1.0 秒）」，无任何伪造回包 |
| 800 ms 延迟 | 送达，RTT 801 ms，回显服务报告 applied_delay=800 |
| 1500 ms 延迟 + 端口复用 | 发送后 1.2 s 时观察：17000 上 `echo-a` 进入保留期（剩余 1192 ms）；此时 `echo-b` 成功复用 17000 并收到自己的回包；1.5 s 后 `echo-a` 的迟到回包到达 → `drop_late`，原客户端超时未收到，复用端口的新客户端也没有收到旧包 |
| 两个端口都处于 `echo-a` 保留期 | 新的 `echo-a` 会话被拒绝，原因写明「17000/17001 处于迟到回包保留期（剩余 2.0 秒）」 |

**网页层面**：用 jsdom 加载真实页面并驱动真实按钮（无头浏览器 Chromium 在本环境下载被限速，
未能安装，故用 jsdom 做 DOM 级验证）：健康指示灯、3 张客户端卡、2 个端口卡、延迟滑块与警告文案、
「全部发送」按钮 → 收件箱渲染真实回包（出口端口/延迟/RTT 都在）、会话表与活动槽位出现→1 s 后
变为保留期槽位→约 3 s 后清空、事件日志追加、重置后日志从 1 条重新开始，无任何 JS 报错。
`scripts/check_compose.py` 校验了 compose/Dockerfile 的服务、DNS 名、端口与 EXPOSE 一致。

## 没完成 / 没验证到的

1. **Docker Compose 没能实际跑起来**：本环境没有 Docker/Podman 守护进程，也无法创建用户命名空间，
   且 `registry-1.docker.io` 不可达。因此镜像构建和容器内 DNS（`echo-a`/`echo-b` 名称解析）、
   容器间网络只做了静态校验（compose YAML 解析 + 与代码常量比对），**没有真正 `docker compose up` 过**。
   所有运行时验证都是在本机进程里做的：同样的代码、同样的 UDP 套接字、上游用 `127.0.0.1` 代替 compose DNS。
2. **页面未在真实浏览器中目测**：只用 jsdom 做了 DOM/交互断言，没有截图或视觉/响应式检查；
   `setInterval` 轮询、CSS 布局、深色主题的观感均未人工确认。
3. 客户端按需求放在**网关容器内**（三个本地 UDP 套接字），没有拆成三个独立客户端容器；
   客户端等待回包的兜底超时是 2.5 s，所以延迟 2 s + 排队时仍可能先判超时（回包到时会被网关按规则丢弃）。
4. 未做的工程化项：无鉴权（演练页默认只绑 127.0.0.1）、状态只在内存中、单进程
   （多 worker 会各自持有互不共享的会话表）、未做压测与长时间稳定性测试、未做 IPv6。
5. 事件日志最多保留 400 条（页面显示最近 120 条），历史不做持久化。
