# 交付说明：UDP 多端口出口运维演练（数百出口端口 · 逐包开销与规模无关）

## 做成了什么

**核心目标**：出口扩到数百个端口后，UDP 网关收发单包的开销不再随会话数或端口数线性增长；
只有「处理实际到期项」和「逐个列出拒绝原因」才与相应数量成正比。

**热路径重写（`app/gateway_core.py`，无 socket、假时钟可测）**

| 机制 | 替代了什么 | 开销 |
| --- | --- | --- |
| `(出口端口, 上游) → 会话` 反向索引 `_by_egress` | 回包时遍历全部会话找归属 | O(1) 字典查询 |
| 每个上游一个「空闲端口下标」小顶堆 `_free` | 新会话遍历端口表 + 全表查占用 | 一次 `heappop`（下标序 = 配置顺序，首个可用端口） |
| 计时小顶堆 `_timers`（到期时刻, 序号, 类型, 键） | 每包 `expire()` 全表扫描会话与保留项 | 只弹出**实际到期**的条目，与到期项数量同阶 |
| 续期压新条目、旧条目弹出时按 `last_forward_at + idle` 校验作废；堆超 `2×(会话+保留)+32` 时重建 | — | 频繁续期下计时记录量仍与存活对象同阶（实测峰值恰好压在 `2×存活+32`） |
| 收发路径先 `_expire_due(now)` 再按 `last_forward_at` 直接判定存活 | 依赖后台清理线程及时跑 | 后台清理（0.2 s 一轮）只负责补记日志事件；清理晚了收发判定仍然正确 |

语义保持不变并逐条有测试：

* 新会话仍按**配置顺序**取首个可用端口（端口列表可以不按数值排序，堆存的是下标）。
* 同一端口在两个上游上的占用与保留期各自独立计算（`(端口, 上游)` 为键，空闲堆按上游分）。
* 保留期从**应失效时刻**（最后一次转发 + 1 s）起算 2 s，与清理线程何时发现无关；
  期间该组合回包丢弃，端口可立即分给另一上游。
* 端口耗尽时照常逐个端口报明原因（被哪个会话占用/保留期剩余多少），
  这是唯一随端口数线性增长的路径（600 端口约 2 ms）。

**数百端口启动配置**

* `compose.yaml`：`EGRESS_PORTS: "${EGRESS_PORTS:-17000-17599}"`（600 个出口端口，
  一个端口一个真实 UDP 套接字）；`EGRESS_PORTS=17000,17001 docker compose up --build`
  可回到原双端口演练。
* `parse_ports` 支持 `17000,17001,17010-17019` 混写（区间 + 列表），校验重复与越界。
* `Dockerfile`：`EXPOSE 8000/tcp 15001/udp 15002/udp 17000-17599/udp`。
* 演练页：端口面板加汇总行（共 N 个：x 占用/保留 · y 空闲），端口数 >24 时默认折叠空闲卡片、
  可勾选展开全部 600 张；拓扑图与「3 并发到 A」按钮文案随端口数自适应。

**脚本与测试**

* `scripts/bench_scale.py`（新）：64/256/1024 端口下 alloc/renew/reply 单包成本、
  拒绝枚举成本、计时堆峰值。
* `scripts/verify_api.py`：按端口数自适应——耗尽/全保留场景仅在端口数 < 3 时演练，否则明确 SKIP。
* `scripts/check_compose.py`：校验 compose 默认 600 端口区间可解析、不与入口/回显端口冲突。
* `tests/test_gateway_scale.py`（新，16 个）：配置序分配、懒到期（不跑清理线程时收发仍按
  最后转发时间判定）、保留期锚定应失效时刻、保留期完整跨过后无残留、计时记录量上界、
  300 端口拒绝逐个枚举、600 端口 24 000 次热路径操作限时、精确到期边界（恰在 1 s/3 s 时刻）。
* `tests/test_integration.py` 新增 260 出口端口真实 UDP 往返（260 个真实套接字）。

## 测到了什么

**单包开销（`scripts/bench_scale.py`，假时钟排除 IO；本机有调度噪声，取多轮代表值）**

| 端口数 | 新会话 alloc | 续期 renew | 回包 reply | 拒绝枚举（允许 O(端口)） |
| --- | --- | --- | --- | --- |
| 64 | ~5–11 µs | ~5–7.6 µs | ~5–6.9 µs | 0.11 ms |
| 256 | ~3–9 µs | ~5–7.8 µs | ~4–8 µs | ~0.5–1.3 ms |
| 1024 | ~4–9.5 µs | ~5–8.4 µs | ~5–7.5 µs | ~2–2.9 ms |

对照旧实现（每包全表扫描，同一基准）：renew 8.3 → 19.4 → **85.7 µs**，reply 10.5 → 25.5 →
**114.7 µs**（64/256/1024 端口，随规模线性放大）。新实现三条热路径在 16 倍规模增长下基本持平，
1024 端口时续期/回包比旧实现快约 10–20 倍，且差距随规模继续线性拉大。
计时堆：100 会话 × 500 次续期（共 5 万次），峰值 232 条 = 上限 `2×100+32`，不随续期次数增长。

**自动化测试**：`pytest -q` → **36 passed**（14 规则 + 16 规模/懒到期/边界 + 6 真实 UDP 集成），
`ruff check` 无告警；`scripts/check_compose.py` 通过。

**真实运行（本机进程，600 出口端口，真实 UDP）**

* 网关绑定 600 个真实出口套接字（`/proc/net/udp` 核实 600/600），`/api/state` 全量快照 ~3–4 ms。
* `scripts/verify_api.py` 对 600 端口实例：场景 1/3/4 全 PASS——三客户端真实回包、
  1→A 与 2→B 共用 17000、3→A 得 17001；800 ms 回包 RTT 801 ms 送达；1500 ms 迟到包被
  `drop_late` 丢弃、echo-b 同期复用 17000 收到自己的回包、旧包未串给新会话；
  场景 2/5（耗尽/全保留）按预期 SKIP。另起 `EGRESS_PORTS=17000,17001` 实例后 5 场景全 PASS，
  耗尽时拒绝原文逐端口列明原因。
* 演练页（jsdom 加载真实页面 + 真实 fetch 打活网关，18 项断言全 PASS）：横幅 600 端口、
  汇总行、空闲折叠/展开 600 张卡片、点「全部发送」后收件箱显示真实回包（出口端口 17000/17001、
  RTT、字节数）、会话表 3 行、1 s 后转保留期卡片、约 3 s 后回空闲，全程无 JS 错误。

## 没完成 / 没验证到的

1. **Docker Compose 没有真正跑起来**：本环境无 Docker/Podman 守护进程，镜像构建、容器内 DNS
   （`echo-a`/`echo-b`）、容器间网络只做了静态校验（`check_compose.py`）。所有运行时验证都在
   本机进程内完成：同一份代码、同样的 UDP 套接字、上游用 `127.0.0.1` 代替 compose DNS。
2. **页面未在真实浏览器中目测**：jsdom 做了 DOM/交互断言，无截图、无视觉检查；
   600 张端口卡片同时展开时的浏览器渲染性能未实测（默认折叠空闲卡片，正常使用时不会同屏 600 张）。
3. 耗尽/全保留场景在 600 端口配置下无法在线演练（3 个客户端占不满），靠 2 端口实例 +
   单测覆盖；多客户端（>3）压测未做。
4. 基准在本机有 ±50% 运行间噪声（共享 CPU），结论依据的是「16 倍规模下开销基本持平」
   这一稳定趋势，不是单次绝对值；未做 C10k 级别的长时稳定性/内存压测。
5. 仍未做的工程化项：无鉴权（演练页默认只绑 127.0.0.1）、状态只在内存、单进程、无 IPv6、
   事件日志最多 400 条不持久化。
